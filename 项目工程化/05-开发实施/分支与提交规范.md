# 分支与提交规范

**版本**：v1.0  
**目标**：让每次变更可追溯、可审阅、可回滚。默认保护 `main`，禁止直接推送。

## 1. 分支模型

| 分支 | 用途 | 来源/合并 |
|---|---|---|
| `main` | 可发布代码 | 仅通过 PR 合并，必须通过检查 |
| `feature/<短名>` | 新功能/迭代 | 从最新 `main` 创建，合入 `main` |
| `fix/<短名>` | 普通缺陷修复 | 从 `main` 创建，合入 `main` |
| `hotfix/<版本>-<短名>` | 线上紧急修复 | 从发布提交创建，合入 `main` 并回合 |
| `docs/<短名>` | 文档、流程、架构说明 | 不改业务逻辑，仍走 PR |
| `chore/<短名>` | 依赖、脚本、构建维护 | 走 PR；注明风险 |
| `release/<版本>` | 发布候选验证 | 从 `main` 创建，验证后合回并打 tag |

分支名使用小写英文、数字和短横线，不包含中文、空格或个人姓名。一个分支只服务一个可验收主题；跨模块大改需拆成可回滚的多个 PR。

## 2. 提交信息

采用 Conventional Commits：

```text
<type>(<scope>): <imperative summary>
```

允许的 `type`：`feat`、`fix`、`docs`、`test`、`refactor`、`perf`、`build`、`ci`、`chore`、`revert`。`scope` 示例：`rag`、`ui`、`security`、`deploy`、`docs`。

示例：

```text
feat(rag): add retrieval strategy switch
fix(security): reject non-loopback Ollama URL
docs(architecture): record hybrid retrieval roadmap
test(rag): cover empty-result fallback
```

提交正文在需要时说明：背景、行为变化、测试命令、迁移/回滚方式。不要在提交信息中写密码、令牌、真实手机号、完整提示词或未经验证的性能数字。

## 3. PR 流程

1. 更新本地 `main`，创建命名分支并关联需求/缺陷编号。
2. 小步提交，保持每个提交可编译；提交前检查敏感信息、生成物和大文件。
3. PR 描述至少包含：问题、方案、范围外内容、测试证据、数据/安全影响、发布和回滚步骤、截图（如 UI 变化）。
4. 至少一名技术审阅者批准；涉及真实数据、模型、网络或认证时追加业务/安全审阅。
5. CI/本地检查通过后使用 Squash Merge（团队若需保留逐提交审计则采用普通合并，但规则需统一）。
6. 合并后删除短期分支；发布分支保留至上线回顾完成。

## 4. 变更分类与审阅门槛

| 变更 | 必须同步 | 额外审阅 |
|---|---|---|
| UI/交互 | 产品验收、截图/测试 | 产品 |
| 数据字段/来源 | 数据字典、迁移/回滚 | 业务数据负责人 |
| 模型/Prompt/RAG | 架构文档、评估集、版本 | 技术 + 安全 |
| 认证/网络/依赖 | 安全边界、部署文档 | 安全/运维 |
| 生产配置 | 环境清单、发布说明 | 发布负责人 |

## 5. 发布标签与回滚

- 使用语义化版本 `vMAJOR.MINOR.PATCH`；MVP 首次发布建议 `v1.0.0`，实际标签以仓库记录为准。
- 发布说明记录提交范围、依赖/模型版本、数据签名、已知问题、监控和回滚提交。
- 回滚优先通过关闭功能开关、恢复上一镜像/包和旧索引完成；禁止直接删除唯一数据源。
- 紧急修复合入后必须补回归测试和复盘记录，避免只修生产分支。
