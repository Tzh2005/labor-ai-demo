# 回滚方案

## 1. 目标与触发条件

回滚目标是先恢复“可用且可解释”的稳定版本，再调查根因。以下任一情况持续超过 10 分钟，或造成数据/隐私风险，应暂停发布并评估回滚：

- Streamlit 无法启动、健康检查连续 3 次失败。
- Ollama 或配置模型不可用，关键问答全部转人工。
- 关键路径错误率明显高于发布前基线（首次上线可用 5% 作为临时阈值）。
- P95 响应时间超过发布前基线的 2 倍且无法在观察窗口内恢复。
- 岗位、工资、福利等事实数据明显错误，或数据/索引与版本不匹配。
- 发现凭证泄露、越权、提示注入绕过或其他安全风险。

阈值是首版运营建议，不是已验证的生产 SLA；每次复盘后应按实际基线调整。

## 2. 回滚级别

| 级别 | 适用情况 | 动作 | 数据影响 |
|---|---|---|---|
| L1 应用文件 | 新代码导致页面/逻辑异常 | 恢复上一稳定构建，保留数据 | 通常无 |
| L2 配置/依赖 | 环境变量、依赖或启动参数异常 | 恢复上一份配置/环境，重启服务 | 通常无 |
| L3 索引/内容 | 岗位、FAQ 或 Chroma 索引异常 | 恢复数据备份或删除后重建索引 | 可能丢失最近内容变更 |
| L4 数据库 | SQLite 损坏或迁移失败 | 停写、备份现状、恢复最近可读快照 | 可能丢失 RPO 内消息 |
| L5 安全隔离 | 凭证泄露或严重攻击 | 立即下线公网入口、轮换凭证、保全证据 | 需专项处置 |

## 3. 回滚前四件事

1. 在事故频道/工单记录时间、版本、症状、影响范围和操作人。
2. 保存当前日志、`git rev-parse HEAD`、配置清单和错误样本；不要覆盖唯一证据。
3. 确认上一稳定版本、备份路径、校验值和恢复负责人。
4. 若涉及安全事件，先执行 L5 隔离并通知负责人，不要为了“快速恢复”删除证据。

## 4. 本地 Windows 回滚

在项目目录执行，路径按实际备份调整：

```powershell
Set-Location D:\1-myFiles\Desktop\AI实习\labor-ai-demo

# 1) 停止当前 Streamlit（在运行窗口按 Ctrl+C）
# 2) 保存当前状态
git rev-parse HEAD | Out-File .rollback-current-sha.txt -Encoding utf8
Copy-Item data data-before-rollback -Recurse

# 3) 切换到已验收标签（确认工作区改动已另存）
git fetch --tags
git switch --detach vX.Y.Z

# 4) 恢复或重建索引（只有确认备份可用后才删除旧索引）
# Remove-Item chroma_db -Recurse -Force
python check_environment.py --build-index

# 5) 启动并按发布前清单冒烟
streamlit run app.py --server.port 8501
```

若没有 Git 标签，使用发布包目录替换应用文件，不要覆盖 `data/labor_ai.db`，除非执行 L4 数据恢复。

## 5. Ubuntu 云端回滚（未在本项目真实执行）

以下是 Runbook 模板，执行前替换占位符并由发布负责人复核：

```bash
export APP_DIR=/opt/labor-ai-demo
export RELEASE_DIR=/opt/releases/labor-ai-demo-vX.Y.Z

sudo systemctl stop labor-ai-demo
sudo tar -czf /opt/backups/pre-rollback-$(date -u +%Y%m%dT%H%M%SZ).tgz \
  -C "$APP_DIR" data .env 2>/dev/null || true

# 将已验收的发布目录切换为当前目录；保留旧目录供审计
sudo mv "$APP_DIR" "${APP_DIR}.failed-$(date -u +%Y%m%dT%H%M%SZ)"
sudo cp -a "$RELEASE_DIR" "$APP_DIR"
sudo chown -R laborai:laborai "$APP_DIR"

# 如需保留现有数据，从备份恢复到新目录后再启动
# sudo tar -xzf /opt/backups/<backup>.tgz -C "$APP_DIR"
sudo systemctl start labor-ai-demo
curl --fail --max-time 5 http://127.0.0.1:8501/_stcore/health
sudo journalctl -u labor-ai-demo -n 100 --no-pager
```

如果服务使用的是 `git checkout` 而非版本目录切换，先复制当前 `data/` 和配置，再执行 `git switch --detach <stable-tag>`；生产环境不建议在工作目录直接做不可追踪的覆盖。

## 6. 数据与索引恢复

- `data/jobs.json` 和 `data/faq.md` 是事实源，恢复后检查 UTF-8、JSON/Markdown 可读性和更新时间。
- `data/labor_ai.db` 包含会话审计记录。恢复前停止写入，保留损坏文件副本，再用 SQLite 完整性检查：

  ```powershell
  sqlite3 data/labor_ai.db "PRAGMA integrity_check;"
  ```

- `chroma_db/` 是可重建索引，不应被视为唯一事实源。优先从 `data/` 重建；若索引与数据签名不一致，禁止直接对外服务。
- 恢复后至少验证：岗位数量、FAQ 关键问题、来源标题、多轮对话写入和人工转接路径。

## 7. 回滚完成判定

- 健康检查连续 3 次通过。
- 关键路径冒烟全部通过，且没有新的高优先级错误。
- 数据库完整性检查通过；恢复时间和可能丢失的数据范围已记录。
- 观察窗口结束后由产品、开发、发布负责人共同确认“恢复/继续调查”。
- 24 小时内补写 `09-复盘运营/复盘模板.md`，即使最终证明无需回滚。

建议首版目标：RTO（恢复服务）≤ 30 分钟，RPO（可接受数据丢失）≤ 24 小时；未建立自动备份前，这只是工作目标，不是承诺。
