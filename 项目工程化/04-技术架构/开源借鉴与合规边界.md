# 开源借鉴与合规边界

## 1. 参考项目

| 项目 | 许可证/状态 | 本项目借鉴点 | 是否复制代码 |
|---|---|---|---|
| [Frappe HRMS](https://github.com/frappe/hrms) | GPL-3.0 | 招聘、入职、生命周期和审批流程 | 否，仅参考流程和实体关系 |
| [RAGFlow](https://github.com/infiniflow/ragflow) | Apache-2.0 | 文档解析、版本、引用和知识库工作区 | 否，当前保留本地 KnowledgeBase |
| [Casbin](https://github.com/apache/casbin) | Apache-2.0 | 主体-角色-项目授权模型 | 否，当前用轻量项目边界，后续评估接入 |

参考源码快照位于仓库工作区的 `参考开源项目/`，该目录已被 `.gitignore` 排除，不会进入业务仓库提交。

## 2. 已吸收的设计思想

### Frappe HRMS

- 把人员从候选/入职到离场看成可追踪生命周期，而不是只有一张人员表。
- 状态变更需要操作者和时间，业务动作与审批/审计分开建模。
- 当前自研实现：`workers`、`placements` 和状态时间线。

### RAGFlow

- 项目知识库应保留文档来源、版本和引用位置，不能只把文本塞进向量库。
- RAG 是文档解释层，关系型数据库仍是业务事实源。
- 当前自研实现：`.txt` / `.md` 项目资料登记、版本与 SHA-256、项目独立索引，以及资料名称/版本来源展示；PDF/Word/OCR、文档审批和引用页码定位仍列入后续迭代。

### Casbin

- 权限判断应围绕“谁（主体）—拥有何种角色—访问哪个项目/资源”展开。
- 项目隔离必须在服务/存储层强制，不依赖 UI 下拉框。
- 当前自研实现：所有新增业务接口带 `project_id`；正式成员、角色和 ABAC 策略列入 V1 权限迭代，暂不宣称生产级 RBAC。

## 3. 合规和许可证边界

1. 不复制 GPL 项目代码、模板或不可独立重写的实现到当前闭源业务代码。
2. Apache-2.0/MIT/BSD 项目如未来实际使用代码或依赖，必须保留 LICENSE/NOTICE、做依赖清单和法务评审。
3. 开源仓库里的业务数据、截图、品牌和第三方资料不进入生产知识库。
4. 不绕过瑞人云或任何 SaaS 的访问控制、导出限制或服务条款；历史数据只通过甲方授权的官方导出/接口进入本库。
5. 参考项目只提供工程启发，不证明其功能、许可证或安全性适合本项目生产使用；发布前必须重新核验上游版本。

## 4. 当前交付范围

已实现：

- 项目默认边界和 `project_id` 字段
- 工人主档（候选人晋级，不复制身份证/明文手机号）
- 派工记录与入场/离场状态
- 在岗人数快照
- 追加写入的审计哈希链演示
- 无候选岗位、长期未推进报名、无在岗人员等确定性风险规则
- 项目驾驶舱、派工页、审计证据页
- 项目级合同/SOP/制度资料登记、版本记录、内容哈希和隔离检索

待开发：

- 正式用户、甲方成员和角色权限
- PDF/Word/OCR 文档处理、文档审批和正式权限/成员模型
- 脱敏 CSV/官方 API 导入、数据校验和重复合并
- 加密字段、KMS/Vault 密钥轮换、独立审计存储
- 证据包导出、备份恢复演练和私有化部署

当前演示库仍不能接收真实身份证、银行卡、工资或社保明细。

## 5. 测试数据与真实数据边界

当前本地库已写入 `demo_seed.py` 生成的合成数据，用于验证驾驶舱、派工和审计页面。该脚本只创建带“测试工人·”前缀的虚构记录，重复运行不会重复创建。

真实数据导入必须另行实现授权的 CSV/官方 API 流程：先确认甲方授权、字段分级、重复合并、错误回滚、访问权限和留存期限，再进入生产库；禁止把瑞人云截图、手抄数据或绕过权限抓取结果直接灌入系统。
