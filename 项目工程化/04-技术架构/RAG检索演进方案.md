# RAG 检索演进方案

**文档版本**：v1.0  
**目标**：在不破坏当前本地优先安全边界的前提下，定义从向量基线到企业级检索的可验证演进路径。  
**状态标记**：`已实现` 表示代码已存在；`待开发` 表示仅有方案，不能对外承诺；`待验证` 表示已实现但尚无评估证据。

## 1. 当前基线（Baseline）

### 1.1 已实现链路

```text
问题 q
  → BGE-large-zh-v1.5 生成归一化向量
  → Chroma similarity_search(k=4)
  → 提示注入过滤
  → 固定 Prompt + 最近 6 条消息
  → Ollama qwen2.5 生成回答
  → 输出安全过滤 + 来源标题
```

实现位置：`knowledge_base.py`（索引与向量检索）、`ai_service.py`（编排与安全）、`app.py`（展示）。岗位文档带有 `type=job`、`job_id`、`location` 等元数据，FAQ 文档带有 `type=faq`。

### 1.2 基线限制

- 只有向量召回，没有词法/BM25 召回；“电子厂名称、岗位编号、数字工资”等精确词可能召回不足。
- 没有 Cross-Encoder 二次排序；向量相似但事实不相关的片段可能进入 Prompt。
- 所有问题都进入完整 RAG，没有意图路由和问题改写。
- 没有语义缓存；重复问题仍调用模型。
- 没有正式标注集和 RAGAS/离线评测结果，不能使用“准确率 80%/90%”等未经测量的数字。
- `chat_stream` 在安全过滤完成后才输出完整回答，不能据此承诺逐 token 低延迟。

## 2. 演进总览

| 阶段 | 能力 | 状态 | 主要收益 | 进入条件 |
|---|---|---|---|---|
| B0 | 向量检索 + 安全过滤 | 已实现 | 语义召回、来源可追溯 | 当前基线 |
| B1 | 向量 + BM25 混合召回 + RRF | 待开发 | 兼顾语义和精确词 | 先完成评估集和可回滚开关 |
| B2 | Cross-Encoder 重排 | 待开发 | 减少 top-k 噪音 | B1 召回集稳定、延迟预算明确 |
| B3 | 查询意图路由/问题改写 | 待开发 | 简单问题少走重链，改善追问 | 有意图标注和失败兜底 |
| B4 | 语义缓存 | 待开发 | 降低重复推理成本 | 明确数据新鲜度、租户和失效策略 |
| B5 | 评估与可观测性 | 待开发/部分已有耗时 | 量化质量和性能 | 贯穿 B1-B4，不得最后补写 |

## 3. B1：混合检索（待开发）

### 3.1 目标架构

```text
q → 查询规范化 ─┬→ 向量召回 top-N（Chroma） ─┐
                └→ 词法召回 top-N（BM25） ───┤→ 去重 → RRF 融合 → top-K
                                                   ↓
                                         注入过滤/元数据过滤
```

推荐初始参数：向量和 BM25 各召回 `N=20`，RRF `k=60`，融合后保留 `K=8`，再交给后续重排。参数必须通过评估集调优，不能把建议值当成最终配置。

### 3.2 设计要点

1. **中文分词**：对岗位名称、工厂名称、地点、工资数字保留词元；分词器版本写入索引元数据。若引入 `jieba`/`rank_bm25`，须固定版本并更新依赖锁定策略。
2. **文档 ID**：使用 `type + job_id` 或 FAQ 稳定 ID 去重，不能使用召回顺序去重。
3. **字段权重**：岗位名称、地点、薪资等结构化字段可建立加权词法索引；权重先在评估集验证。
4. **空结果和异常**：任一检索器失败时记录错误并降级到另一检索器；两者都失败才返回转人工，不把异常吞掉。
5. **兼容开关**：用配置开关选择 `vector` 或 `hybrid`，默认保持 `vector`，便于灰度和回滚。

### 3.3 RRF 伪代码

```python
def rrf(rank_lists: list[list[str]], rrf_k: int = 60) -> list[str]:
    scores: dict[str, float] = {}
    for ranked_ids in rank_lists:
        for rank, doc_id in enumerate(ranked_ids, start=1):
            scores[doc_id] = scores.get(doc_id, 0.0) + 1 / (rrf_k + rank)
    return sorted(scores, key=scores.get, reverse=True)
```

伪代码仅表达算法，不代表当前仓库已实现。新增实现应保留每个召回器的 rank、分数和版本，便于离线分析。

## 4. B2：重排序（待开发）

### 4.1 方案

对 B1 融合后的候选（建议 8～20 条）构造 `(query, document)` 对，使用本地 Cross-Encoder（例如经评审的中文 reranker）打分，按分数取最终 top-3/4，再执行注入过滤和 Prompt 构建。

### 4.2 约束

- 模型必须支持离线缓存；模型许可、磁盘占用和 CPU/GPU 资源要在技术评审中确认。
- 重排失败时回退到 RRF 顺序，不得让单个模型异常导致全链路不可用。
- 记录 `retrieval_stage`、候选数、最终数、rerank 耗时和模型版本；回答中不展示内部分数。
- 先做离线对比，再决定是否默认开启。没有评估证据时标记 `待验证`。

## 5. B3：查询路由与多轮问题改写（待开发）

### 5.1 路由类别

| 类别 | 示例 | 推荐路径 | 兜底 |
|---|---|---|---|
| 闲聊/问候 | “你好” | 固定短回复，不查库 | 人工转接 |
| FAQ | “入职需要什么证件” | FAQ 过滤 + 向量/混合检索 | 完整 RAG |
| 岗位查询 | “石岩有什么普工” | 岗位元数据过滤 + 检索 | 完整 RAG |
| 追问 | “工资多少” | 结合会话改写为独立问题 | 使用原问题检索 |
| 不确定/高风险 | “能保证月底拿到多少” | 检索并强制人工确认 | 不生成承诺 |

路由器应先使用确定性规则，低置信度才调用轻量分类模型；任何路由结果都必须允许回退到当前基线链路。不要为了“节省一次检索”跳过安全过滤和来源记录。

### 5.2 问题改写

改写器把“工资多少？”与最近对话中的岗位实体合并为独立问题，例如“石岩电子厂普工工资多少？”。改写结果必须保留原问题、改写问题、会话 ID 和模型版本，禁止把改写文本直接当作用户原话写入审计记录。改写失败或检测到新增实体时使用原问题并提示人工确认。

## 6. B4：语义缓存（待开发）

### 6.1 适用边界

缓存只适用于低风险、来源稳定的 FAQ 或岗位查询。工资、福利、岗位状态、招聘有效期变化后必须主动失效；不同用户/租户的私有信息不能共享缓存。当前项目没有语义缓存实现，也没有可直接启用的缓存后端。

### 6.2 最小设计

- Key：规范化问题 + 知识库版本 + Prompt 版本 + 模型版本 + 权限范围。
- Value：回答、来源 ID、生成时间、过期时间、检索配置版本。
- 命中前：先校验知识源签名和敏感问题规则；命中后仍显示来源。
- 失效：`jobs.json`/`faq.md` 签名变化、岗位状态变化、Prompt/模型变化或 TTL 到期。
- 指标：命中率、误命中率、平均节省耗时、过期命中数。

不要使用进程内无上限字典作为生产缓存；若云端启用，应选有容量、TTL、权限和监控的存储。

## 7. 评估与验收（贯穿所有阶段）

### 7.1 评估集

第一版建立 30～50 条人工标注样本，覆盖：岗位名称/地点/工资精确词、FAQ、否定条件、数字、追问、无答案、提示注入和高风险承诺。每条记录：问题、期望来源 ID、关键事实、允许的人工转接结果。

### 7.2 指标定义

| 指标 | 定义 | 采集时点 |
|---|---|---|
| Recall@K | 期望来源是否出现在候选 top-K | 检索阶段 |
| MRR/nDCG | 相关来源在候选中的排序质量 | 检索/重排阶段 |
| Faithfulness | 回答事实是否能被来源支持 | 生成后人工或评测框架 |
| Answer relevancy | 回答是否切题 | 生成后 |
| 无来源回答率 | 没有可靠来源仍生成事实性回答的比例 | 运行日志 |
| P50/P95 延迟 | 从提问到完整回答的耗时 | 运行日志 |
| 缓存命中率 | 命中且通过新鲜度校验的请求比例 | 缓存阶段 |

当前仓库尚未生成正式评估报告，所有目标数值均应在数据测量后填写。禁止在 README、简历或发布说明中把方案预期提升写成实测结果。

## 8. 发布与回滚策略

1. 新检索能力以配置开关和版本号发布，默认保留 B0。
2. 先离线评估，再用小流量/内部用户灰度；比较质量、延迟、错误和人工转接率。
3. 出现事实性回退、延迟超预算或内存异常时，关闭开关回到 B0；保留候选日志用于定位。
4. 每次索引、嵌入、分词器、重排模型升级都生成可识别版本，并保留旧索引直到新版本通过验收。
