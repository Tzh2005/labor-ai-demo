# 系统架构说明

**文档版本**：v1.0（MVP 基线）  
**适用范围**：`labor-ai-demo` 本地演示版与后续受控部署  
**维护人**：技术负责人  
**最后更新**：2026-09-21

## 1. 目的与架构结论

本文记录当前代码真实落地的组件、边界和数据流，作为技术评审、开发拆分、测试设计和上线评审的共同基线。当前系统是“本地优先”的 Streamlit 单体应用：岗位与 FAQ 数据存储在项目目录，向量索引存储在本地 Chroma，模型通过本机 Ollama 调用，会话审计写入本地 SQLite。

以下能力属于当前基线：

- Streamlit 页面、密码认证、岗位浏览和自然语言问答。
- BGE 中文嵌入 + Chroma 向量相似度检索。
- Ollama `qwen2.5:3b`（可通过环境变量切换）生成回答。
- 来源标题回显、最近对话上下文、SQLite 会话记录。
- 索引按源文件签名增量判断，重建时先写临时目录再替换。
- 本地 Ollama 地址校验、检索内容注入过滤、输出安全过滤、输入长度和频率限制。

以下能力不能在第一版对外宣称已具备：Cross-Encoder 重排、意图路由、语义缓存、RAGAS 评测、集中式指标平台、项目级权限与不可篡改审计、真正的公网生产高可用。当前混合检索为“已实现/待验证”的本地词法 + 向量 RRF 方案，详见 `RAG检索演进方案.md`。

## 2. 逻辑架构

```text
┌─────────────────────────────────────────────────────────────────────┐
│                         Streamlit 展示层                            │
│ app.py：认证、聊天、岗位筛选、候选人匹配、状态提示、来源展示、限流 │
└──────────────────────────────┬──────────────────────────────────────┘
                               │ 函数调用
┌──────────────────────────────▼──────────────────────────────────────┐
│                         应用服务层                                  │
│ AIService：问题校验 → 检索 → 安全过滤 → Prompt → Ollama → 清洗      │
│ ConversationStore：会话、岗位、候选人和报名记录；来源 JSON、UTC 时间│
└───────────────┬───────────────────────┬──────────────────────────────┘
                │                       │
┌───────────────▼──────────────┐  ┌─────▼─────────────────────────────┐
│ KnowledgeBase                 │  │ 本地推理服务                       │
│ BGE Embeddings + Chroma       │  │ Ollama / qwen2.5                  │
│ jobs.json + faq.md            │  │ 仅允许 loopback 地址              │
└───────────────┬──────────────┘  └────────────────────────────────────┘
                │
┌───────────────▼─────────────────────────────────────────────────────┐
│ 本地持久化                                                          │
│ data/jobs.json · data/faq.md · chroma_db/ · data/labor_ai.db         │
└─────────────────────────────────────────────────────────────────────┘
```

### 2.1 组件职责

| 组件 | 代码/目录 | 职责 | 当前状态 |
|---|---|---|---|
| Web/UI | `app.py` | 页面、登录、问题输入、岗位筛选、回答和来源渲染 | 已实现 |
| AI 编排 | `ai_service.py` | Ollama 配置校验、检索编排、提示词、输出清洗 | 已实现 |
| 知识库 | `knowledge_base.py` | 文档构建、切分、嵌入、Chroma 持久化和查询 | 已实现 |
| 业务存储 | `conversation_store.py` | SQLite 初始化、会话、岗位、候选人和报名写入 | 已实现（单项目） |
| 岗位数据 | `data/jobs.json` | 岗位结构化数据源 | 已实现（演示数据） |
| FAQ 数据 | `data/faq.md` | 常见问题文本数据源 | 已实现（演示数据） |
| 向量索引 | `chroma_db/` | BGE 向量及 Chroma 元数据 | 本地构建产物 |
| 环境诊断 | `check_environment.py` | 依赖、数据、Ollama、模型和索引检查 | 已实现 |

代码层之间只通过公开函数/类交互。UI 不应直接操作 Chroma 或 SQLite；新增检索能力应集中在 `KnowledgeBase` 或独立检索服务中，避免业务页面产生第二套检索逻辑。

## 3. 关键数据流

### 3.1 启动与认证

1. Streamlit 加载 `app.py`，读取 `DEMO_PASSWORD`。
2. 未配置密码时停止渲染并提示管理员配置；密码比较使用常量时间比较。
3. 认证成功后初始化缓存的 `ConversationStore`，读取岗位列表，并检查 Ollama 和索引状态。
4. `AIService` 第一次被调用时校验 `OLLAMA_BASE_URL`、模型可用性并加载 `KnowledgeBase`。

### 3.2 问答链路

```text
用户输入
  → 长度校验（≤500）与会话级频率限制（10 次/分钟）
  → 默认混合检索（向量 + 本地词法 RRF；可回退纯向量）
  → 丢弃疑似提示注入的文档
  → 将文档、最近 6 条消息和问题放入固定 Prompt
  → 本机 Ollama 生成完整文本
  → 输出安全过滤；命中危险模式则转人工
  → 页面显示回答和来源标题
  → user/assistant 消息写入 SQLite
```

当前 `chat_stream` 为“先完整生成、后一次性输出”的安全缓冲策略，不能把它描述为真正的逐 token 安全流式传输。页面仍保留 Streamlit 流式接口，后续若改为增量输出必须重新做注入安全评审。

### 3.3 索引构建链路

1. 读取 `jobs.json` 并校验必填字段。
2. 每个岗位形成一个 `type=job` 文档；FAQ 使用递归切分器形成 `type=faq` 文档。
3. 计算 `jobs.json` 和 `faq.md` 的 SHA-256 源签名。
4. 签名未变化时复用 `chroma_db/`；变化时在临时目录构建新索引。
5. 构建成功后备份旧目录并替换，写入 `.data_signature`；构建失败时保留原索引。

## 4. 部署拓扑与边界

### 4.1 MVP 本地拓扑

```text
浏览器 ──HTTP──> Streamlit:8501 ──HTTP──> Ollama:11434 (loopback)
                         │
                         ├──读── data/jobs.json / data/faq.md
                         ├──读写── chroma_db/
                         └──读写── data/labor_ai.db
```

所有数据默认留在同一台机器。`OLLAMA_BASE_URL` 只允许 `localhost`、`127.0.0.1` 或 `::1`，禁止把模型请求指向公网或云元数据地址。若未来拆成服务，必须重新设计认证、TLS、网络 ACL、租户隔离和密钥管理，不能只修改 URL。

### 4.2 受控云部署前置条件（待开发/待评审）

- 使用反向代理（TLS、请求体限制、访问日志脱敏）和进程管理器；不把 `streamlit run` 开发进程直接暴露公网。
- Ollama、应用、数据卷分离，明确备份与恢复演练。
- 增加集中式日志、指标、健康检查和告警；配置密钥不得写入镜像或仓库。
- 通过压测、数据脱敏评审、最小权限评审后才允许接入真实招聘数据。

## 5. 非功能基线

| 维度 | MVP 基线 | 生产准入要求 |
|---|---|---|
| 可用性 | 单机、人工启动/重启 | 明确 SLO、进程托管、健康检查和回滚 |
| 性能 | 本地 CPU，耗时以页面实测为准 | 用评估集和压测记录 P50/P95，不能沿用演示印象 |
| 数据 | 演示岗位和 FAQ，本地文件 | 数据分级、加密备份、留存期限、删除流程 |
| 安全 | 密码、loopback、输入/输出限制 | TLS、身份体系、审计、限权、漏洞扫描 |
| 可观测性 | 页面显示最近耗时，SQLite 留痕 | 指标、日志关联 ID、告警和值班 Runbook |
| 扩展性 | 单体模块化 | 先保持模块边界，再按瓶颈拆服务 |

## 5.1 V1 数据主权目标架构（待开发）

V1 不把当前 SQLite 单机库直接包装成多租户生产能力。上线前需把项目边界下沉到服务和存储层，并在每次读取、写入、导出、同步时强制校验。

```text
甲方成员/劳务运营人员
        │ 身份认证 + 项目角色
        ▼
应用/API 层 ── 强制 project_id + 权限策略 ──> 项目业务数据单元
        │                                      ├── 岗位/候选人/报名/审批
        ├── 审计事件（追加写 + 哈希链/签名） ──> 证据与审计存储
        ├── KMS/Vault 数据密钥 ──────────────> 敏感字段加密
        └── 单向同步适配器 ───────────────────> 外部效率工具（只出不回写）
```

### 强制设计约束

1. 每个业务表、向量集合、对象存储路径和缓存键都须包含 `project_id`；服务层根据登录上下文注入，客户端不得自由指定。
2. 项目隔离采用“逻辑租户 + 项目独立数据单元”的渐进方案：首个生产客户优先独立数据库/密钥；共享库只允许在行级策略、备份恢复和越权测试已通过时使用。
3. 敏感字段采用信封加密：数据密钥只用于单项目数据，主密钥由 KMS/Vault 托管；应用日志、向量库和分析平台不保留明文。
4. 审计事件仅追加，事件包含前一事件哈希、请求关联 ID、操作者、项目、动作、对象、结果和 UTC 时间；归档副本必须可校验。
5. 数据导出是产品承诺的一部分：导出包应含数据、审计清单、版本和校验和。禁止通过不提供导出能力制造锁定。
6. 外部同步默认单向、最小字段、可重放；未通过接口评审不得向甲方或效率工具写入数据。

## 6. 失败处理与降级

| 故障 | 用户可见行为 | 运维动作 |
|---|---|---|
| Ollama 不可达 | 页面提示服务暂不可用 | 检查 `ollama serve`、端口和模型状态 |
| 模型未安装 | 侧栏显示 `ollama pull` 命令 | 安装配置模型并重新运行诊断 |
| 索引不存在/源变更 | 首次查询触发构建；失败则通用错误 | 检查磁盘、嵌入模型缓存和数据格式 |
| 检索结果为空或全被过滤 | 返回转人工消息，不调用模型 | 检查数据质量和注入过滤日志 |
| SQLite 写入冲突 | 页面保留通用错误，详细信息进日志 | 检查磁盘、WAL 文件和并发量 |

## 7. 架构决策记录（ADR 摘要）

| 决策 | 选择 | 原因 | 后续复审条件 |
|---|---|---|---|
| 模型运行方式 | 本地 Ollama | 演示零外部 API 成本，数据不出机 | 需要公网、多用户或 GPU 扩容时复审 |
| 向量库 | Chroma 本地持久化 | 安装简单、适合 MVP | 数据量、并发或高可用超出单机时复审 |
| 会话库 | SQLite WAL | 低运维成本，便于审计演示 | 多实例部署或写入量上升时迁移 |
| 索引切换 | 临时目录 + 替换 | 避免构建失败破坏旧索引 | 引入对象存储/版本索引时复审 |
| 输出安全 | 缓冲后清洗 | 防止危险 token 先展示 | 真流式输出或更复杂攻击时升级方案 |
| 客户留存 | 数据可导出 + 专属治理 | 用可信流程和证据留存，不靠锁死数据 | V1 项目模型、审计与导出通过验收后 |
