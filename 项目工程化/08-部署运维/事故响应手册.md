# 事故响应手册

## 1. 原则

先保护用户、数据和证据，再恢复服务；先陈述已知事实，再提出假设。事故沟通不归咎个人，复盘聚焦系统、流程和防护缺口。

## 2. 分级

| 级别 | 定义 | 示例 |
|---|---|---|
| P0 | 安全、隐私或数据完整性重大风险 | 密码泄露、敏感会话外泄、恶意公网访问 |
| P1 | 核心服务大面积不可用或明显错误 | Streamlit/Ollama 全量不可用、错误岗位内容大面积展示 |
| P2 | 部分功能或性能受损，有可行绕行 | 单页异常、模型延迟显著升高 |
| P3 | 低风险缺陷或体验问题 | 文案错误、非关键样式异常 |

## 3. 事故角色

| 角色 | 责任 |
|---|---|
| 事件指挥（IC） | 定级、节奏、决策、升级与关闭 |
| 技术处置 | 收集证据、隔离、恢复、验证 |
| 沟通负责人 | 向业务、用户和管理者同步已确认信息 |
| 记录员 | 维护时间线、命令、证据和决定 |

小团队可兼任，但 P0/P1 必须明确一名事件指挥，避免多人同时改环境。

## 4. 前 15 分钟清单

1. 建立事故记录：编号、发现时间、环境、版本/Git SHA、发现人。
2. 判断是否涉及安全或数据：是则先限制公网入口、暂停发布、保留日志和文件副本。
3. 执行最小健康检查：Streamlit、Ollama、磁盘、最近日志。
4. 评估影响：受影响用户、功能、数据范围、开始时间、是否仍在扩大。
5. 选择恢复路径：修复、降级（人工转接/暂时关闭问答）或回滚。
6. 每 30 分钟（P0/P1）同步一次“已知影响、正在做什么、下次更新时间”。

## 5. 处置流程

```text
发现 → 定级 → 隔离/止损 → 证据保全 → 恢复/回滚 → 验证 → 对外说明 → 复盘
```

### 服务不可用

```bash
# Ubuntu 模板
sudo systemctl status labor-ai-demo ollama --no-pager
sudo journalctl -u labor-ai-demo -n 200 --no-pager
curl --max-time 5 http://127.0.0.1:8501/_stcore/health
curl --max-time 5 http://127.0.0.1:11434/api/tags
df -h
```

先读取日志和状态，再重启单个故障服务；重启后做健康检查和关键路径冒烟。连续失败、版本相关或数据风险时执行 `07-发布上线/回滚方案.md`。

### 数据错误或索引异常

1. 暂停相关内容更新；若影响招聘事实，临时切换人工确认。
2. 保存当前 `data/`、索引签名和错误样本。
3. 确认事实源后恢复数据并重建索引。
4. 用固定问答集验证工资、地点、福利和来源，确认后再开放。

### 安全/凭证事件

1. 立即限制公网入口或停止服务，禁止继续共享疑似泄露的凭证。
2. 保存访问日志、时间线、配置元数据和相关文件校验值；不要删除证据。
3. 由授权人轮换 `DEMO_PASSWORD` 和任何受影响凭证，检查文件权限和 Git 历史。
4. 评估受影响数据与通知义务；涉及个人信息时按组织合规流程升级。
5. 恢复前完成漏洞修复、独立复核和安全验证。

## 6. 沟通模板

内部首次通知：

```text
[P1] 劳务 AI 助手服务异常
发现时间：YYYY-MM-DD HH:mm（时区）
影响：已确认/待确认的用户与功能范围
当前版本：vX.Y.Z / SHA
已采取措施：
下一次更新时间：HH:mm
事件指挥：姓名
```

恢复通知：

```text
服务已于 YYYY-MM-DD HH:mm 恢复。影响窗口：...；恢复措施：...；
当前仍在观察：...；复盘计划：YYYY-MM-DD。
```

不要在群组中粘贴密码、完整用户聊天内容、服务器 IP/攻击细节或未经确认的原因。

## 7. 关闭与复盘

事故只有在服务恢复、数据风险处置完成、用户影响已记录、监控恢复和负责人确认后才可关闭。P0/P1 在 24 小时内启动复盘，P2 在 5 个工作日内评估是否需要复盘；模板见 `09-复盘运营/复盘模板.md`。
