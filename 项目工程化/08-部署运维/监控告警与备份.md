# 监控、告警与备份

## 1. 监控目标

第一版以“尽早发现不可用、数据风险和体验明显退化”为目标，不假设已经接入某个付费 APM 或云监控平台。监控数据应避免收集完整聊天内容和密码。

## 2. 最小观测清单

| 层级 | 信号 | 采集方式 | 初始告警建议 | 处置方向 |
|---|---|---|---|---|
| 入口 | Streamlit 健康检查 | `/_stcore/health` | 连续 3 次失败 | 查服务/反代日志，必要时回滚 |
| 模型 | Ollama tags/API | `/api/tags` | 连续 3 次失败或模型缺失 | 恢复 Ollama/模型，转人工 |
| 应用 | 启动异常、Traceback | systemd journal 或本地终端日志 | 任一新重复错误 | 关联版本，停止扩散 |
| 性能 | 首字/全文响应时间 | 应用页面人工抽样；后续接入指标 | P95 超基线 2 倍持续 10 分钟 | 看 CPU/内存/模型/并发 |
| 数据 | 数据文件时间、SQLite 完整性 | 定时校验 | 事实源缺失、DB 校验失败 | 停写、备份、恢复 |
| 主机 | CPU、内存、磁盘 | OS/云监控 | 磁盘 >80%，内存 >85% 持续 10 分钟 | 清理可再生缓存或扩容 |
| 安全 | 登录异常、配置文件权限、异常流量 | Nginx/系统日志 | 凭证疑似泄露/异常访问 | 隔离、轮换、保全证据 |

“P95”“错误率”等需要先建立真实基线。首次上线前至少记录 10 次关键问答的首字和全文响应时间，发布后用相同问题集比较。

## 3. 健康检查与日志操作

### Windows 本地

```powershell
Invoke-WebRequest http://127.0.0.1:8501/_stcore/health -UseBasicParsing
Invoke-WebRequest http://127.0.0.1:11434/api/tags -UseBasicParsing
Get-NetTCPConnection -LocalPort 8501 -ErrorAction SilentlyContinue
Get-PSDrive C
```

### Ubuntu 云端（模板）

```bash
curl --fail --max-time 5 http://127.0.0.1:8501/_stcore/health
curl --fail --max-time 5 http://127.0.0.1:11434/api/tags
sudo systemctl is-active labor-ai-demo
sudo journalctl -u labor-ai-demo --since '15 minutes ago' --no-pager
df -h /opt/labor-ai-demo /opt/backups
free -h
```

建议将健康检查接入组织已有的监控平台；没有平台时，可由受控的定时任务运行检查并向指定值班渠道告警。定时任务不得把环境变量、聊天正文或密码写入通知。

## 4. 告警分级与响应时限

| 级别 | 示例 | 首次响应 | 通知 |
|---|---|---|---|
| P0 | 数据泄露、严重安全事件、所有用户无法使用 | 15 分钟 | 负责人、技术、业务 |
| P1 | 核心问答不可用、持续大面积错误 | 30 分钟 | 值班、发布负责人、产品 |
| P2 | 性能明显下降、单项功能异常 | 4 小时 | 值班和相关负责人 |
| P3 | 文案、低风险体验问题 | 下一个工作日 | 需求池/迭代负责人 |

真实 SLA 应在有人员排班、监控覆盖和历史数据后另行确定；上表是 MVP 运维目标。

## 5. 备份策略

### 5.1 分类

| 资产 | 是否备份 | 频率 | 留存 | 说明 |
|---|---|---|---|---|
| `data/jobs.json`、`data/faq.md` | 是 | 每次发布前 + 每日 | 30 天起 | 事实源，需审核版本 |
| `data/labor_ai.db` | 是 | 每日 + 每次发布前 | 30 天起 | 会话审计；按隐私策略可更短 |
| `chroma_db/` | 可选 | 每次重大索引变更前 | 7 天起 | 可由事实源重建，不是唯一副本 |
| `.env`/`/etc/labor-ai-demo.env` | 不进常规备份包 | 仅受控密钥库 | 按密钥策略 | 绝不进入 Git 或普通共享盘 |
| 应用版本/依赖清单 | 是 | 每次发布 | 与版本一致 | 标签、构建产物、校验值 |
| 日志 | 是（脱敏后） | 按平台 | 7-30 天 | 不记录密码和完整敏感聊天 |

### 5.2 备份命令示例

Windows PowerShell：

```powershell
Set-Location D:\1-myFiles\Desktop\AI实习\labor-ai-demo
$stamp = Get-Date -Format 'yyyyMMddTHHmmss'
$backupRoot = "D:\labor-ai-backups\$stamp"
New-Item -ItemType Directory -Path $backupRoot -Force | Out-Null
Copy-Item data\jobs.json, data\faq.md -Destination $backupRoot
Copy-Item data\labor_ai.db -Destination $backupRoot -ErrorAction Stop
Get-FileHash "$backupRoot\*" -Algorithm SHA256 | Out-File "$backupRoot\SHA256SUMS.txt" -Encoding utf8
```

Ubuntu：

```bash
export APP_DIR=/opt/labor-ai-demo
export BACKUP_ROOT=/opt/backups/labor-ai-demo/$(date -u +%Y%m%dT%H%M%SZ)
sudo install -d -o laborai -g laborai -m 0750 "$BACKUP_ROOT"
sudo -u laborai cp "$APP_DIR/data/jobs.json" "$APP_DIR/data/faq.md" "$APP_DIR/data/labor_ai.db" "$BACKUP_ROOT/"
sudo -u laborai sha256sum "$BACKUP_ROOT"/* > "$BACKUP_ROOT/SHA256SUMS.txt"
```

数据库正在写入时应先短暂停止应用，或使用 SQLite 安全备份机制；不要仅复制正在变化的 WAL 数据库文件后就假定备份一致。

### 5.3 恢复演练

至少每月或每次重大变更后执行一次非生产恢复演练：

1. 选择一个已校验备份，复制到隔离目录。
2. 校验 SHA-256、JSON 可读性和 SQLite `PRAGMA integrity_check`。
3. 用恢复的数据重建 Chroma 索引并完成关键路径冒烟。
4. 记录恢复用时、遗漏项和改进动作。

未经演练的备份只能称为“已生成”，不能称为“可恢复”。

## 6. 数据最小化与留存

- 当前 SQLite 记录会话 ID、角色、正文、来源和 UTC 时间。运营指标优先聚合计数，不导出完整对话正文。
- 导出用于分析时移除或掩码电话号码、身份证号、住址、密码和其他个人信息。
- 设定数据保留期、访问角色和删除流程后再面向真实用户长期运行；首版建议由业务和合规负责人确认。
- 发现敏感信息误写入日志或备份时，按 `事故响应手册.md` 的安全事件流程处置。
